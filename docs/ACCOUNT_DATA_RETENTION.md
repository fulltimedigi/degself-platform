# الاحتفاظ بالبيانات عند حذف الحساب

توثيق واقعي لما يحدث فعليًا عند حذف حساب مستخدم نهائي عبر
`POST /api/account/delete`. المصدر: مخطط قاعدة البيانات + migration `035` +
كود المسار. حُقِّق مقابل قاعدة الإنتاج بتاريخ 2026-08-08.

الحذف يبدأ من هوية Supabase Auth نفسها
(`auth.admin.deleteUser`)، ثم تنتشر آثاره عبر مفاتيح خارجية (FK).

## هوية المصادقة (auth.users)

تُحذف. هي نقطة البداية للحذف.

## profiles

تُحذف تلقائيًا عبر **ON DELETE CASCADE** من `profiles.id → auth.users(id)`.

## user_favorites

تُحذف تلقائيًا عبر **ON DELETE CASCADE** من `user_favorites.user_id → auth.users(id)`.
هذا مصدر الحقيقة لمحفوظات المستخدم المسجَّل (الزائر يستخدم localStorage فقط).

## سجل الأدمن القديم (public.admins)

جدول `public.admins` مرتبط بـ`profiles(id)` عبر **ON DELETE CASCADE**.
لكن **الحذف الذاتي يُرفض** إذا وُجد صفٌّ للمستخدم في هذا السجل: يعيد المسار
`HTTP 409` بالرمز `ACCOUNT_HAS_PRIVILEGED_ROLE`، ولا تُحذف الهوية الإدارية
ضمنيًا. إزالة الصلاحية الإدارية إجراء منفصل قبل الحذف.

## admin_credentials

نموذج مستقل تمامًا: صفٌّ مفرد (singleton) يخزّن hash كلمة مرور دخول لوحة
الإدارة. **غير مرتبط** بـ`auth.users` ولا يمثّل المستخدم الحالي، **ولا يُحذف**
مع حساب المستخدم. لا علاقة له بهوية المستخدم النهائي.

## الكراجات المملوكة (claimed workshops)

`workshops.claimed_by → profiles(id)` (حاليًا **NO ACTION**)، مع حقل منفصل
`workshops.is_claimed`. **الحذف الذاتي يُرفض** إذا كان المستخدم يملك أي كراج
(`claimed_by = user`): يعيد المسار `HTTP 409` بالرمز
`ACCOUNT_HAS_CLAIMED_WORKSHOP`.

نقصد ذلك عمدًا: تصفير `claimed_by` وحده قد يترك `is_claimed = true` بلا مالك،
وتصفير `is_claimed` تلقائيًا يعني إلغاء ملكية الكراج كأثر جانبي لحذف الحساب —
وهو قرار ملكية/أعمال، لا تنظيف FK. لذلك لا نغيّر هذا الـFK في migration `035`،
ونوقف الحذف حتى تُنقل الملكية أو تُحلّ عبر workflow مستقل (خارج نطاق هذا العمل).

## community_mentions

الإسناد (attribution) عبر `community_mentions.matched_by → profiles(id)`.
عدّلت migration `035` هذا الـFK إلى **ON DELETE SET NULL** (بعد التحقق أن
العمود nullable وأن الحالة كانت NO ACTION). عند حذف الحساب:
**يبقى صفّ الإشارة كما هو** ويصبح `matched_by = NULL` فقط. لا تُحذف الإشارات
ولا تُعدّل بقية حقولها.

## quotes

جدول `quotes` **لا يحتوي عمود `user_id`** ولا مفتاح خارجي إلى هوية الحساب
(حُقِّق: 0 أعمدة `user_id`). هي سجلّات تشغيلية (اسم ورقم هاتف يدخلهما العميل في
النموذج)، و**لا تُحذف** تلقائيًا عند حذف الحساب لأنها غير مرتبطة بهوية Auth.

أي طلب حذف لهذه السجلّات يتطلب معالجة منفصلة عبر المُعرّفات المخزَّنة فعليًا
(مثل رقم الهاتف). **هذه فجوة معروفة في نموذج البيانات** تُوثَّق صراحةً هنا.

## offers

`quote_offers.quote_id → quotes(id)` عبر **ON DELETE CASCADE**. العروض تابعة
للطلب (quote) وليست مرتبطة بحساب المستخدم؛ تتبع مصير الطلب نفسه، ولا تُحذف عبر
هوية Auth.

## reviews

جدول `reviews` **بلا مفتاح خارجي لحساب المستخدم** (0 أعمدة `user_id`).
النموذج مجهول الهوية ويُدار يدويًا (pending/approved/rejected). التقييمات
**تبقى** ولا تتأثر بحذف الحساب.

## تحليلات المنتج (product analytics)

PostHog يُستقبَل عبر وكيل first-party داخلي (`/api/ds-b1`) بقائمة سماح صريحة
للأحداث والخصائص (انظر `src/lib/product-analytics.ts`). لا يُرسَل **معرّف
مستخدم Supabase** ولا يُنشأ person profile (تؤكّده اختبارات العقد
`product-analytics-*`). بما أنه لا يُخزَّن أي معرّف حساب في التحليلات، فإن حذف
الحساب **لا يحذف** بيانات تحليلية تاريخية — لأنها غير مرتبطة بالحساب أصلًا.
مزوّدو Vercel Analytics وSnap Pixel كذلك لا يتلقّون معرّف حساب Supabase.

## أثر الحذف الصلب للكراج على المحفوظات

`user_favorites.place_id → workshops(place_id)` عبر **ON DELETE CASCADE**
عمدًا. لكن `workshops` كتالوج مستورَد/مُجمَّع خضع تاريخيًا لعمليات حذف صلب.

> الحذف الصلب لصفّ كراج يحذف أيضًا كل المحفوظات التي تشير إليه. يجب أن يستخدم
> التنظيف الدوري للكتالوج حالات الإزالة الناعمة الموجودة مثل
> `active` / `permanently_closed` حيثما كان مناسبًا. وأي حذف صلب متعمَّد يجب
> أن يتعامل صراحةً مع أثره على المحفوظات.

الحذف الصلب ليس ممنوعًا تقنيًا للأبد؛ القاعدة هي تفضيل الإزالة الناعمة
والتعامل الواعي مع الأثر عند الحذف الصلب المتعمَّد.
